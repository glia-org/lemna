# Post-processing forward-only flow-writing output on macOS

Scope: what can clean up raw text from a forward-only session (typos, missing punctuation, run-on paragraphs, no formatting), from "do nothing" to "on-device AI rewrite". Each finding is tagged: **[docs]** vendor documentation, **[vendor claim]** marketing or author claims not independently checked, **[measured]** a reported measurement, **[review]** independent hands-on review or anecdote, **[paper]** research paper. Research date: 2026-10-27.

## 1. Built-in macOS facilities: NSSpellChecker, Writing Tools, Foundation Models, NLTokenizer, dictation commands

### Takeaway
macOS offers three tiers for free: NSSpellChecker (word-level spelling and autocorrect, offline, callable from Rust through objc2, but grammar results outside NSTextView are unreliable), Apple Intelligence Writing Tools (full proofread of spelling, grammar and punctuation on M1+ with macOS 15.1+, but text may go to Private Cloud Compute, review is often all-or-nothing, long documents fail, and the deepest integration into a custom-drawn view is expensive), and the Foundation Models framework (macOS 26+, on-device ~3B model, 4,096-token window for input plus output, no published proofreading quality data). Writing Tools also ships as Shortcuts actions in the 26 releases, which makes a "hand-off" design possible without any integration in the tool.

**Foundation Models framework**
- [docs] `SystemLanguageModel` requires macOS/iOS/iPadOS/visionOS 26.0; apps check `availability` (`.appleIntelligenceNotEnabled`, `.modelNotReady` while downloading, etc.) — [Apple SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel)
- [docs] "a large language model with 3 billion parameters, each quantized to 2 bits"; "optimized for use cases like summarization, extraction, classification"; "not designed for world knowledge or advanced reasoning"; runs on-device and offline; "can only run on Apple Intelligence-enabled devices in supported regions"; errors to handle include guardrail violation, unsupported language and context window exceeded; guided generation (`@Generable`, `@Guide`) "guarantees structural correctness using … constrained decoding" — [WWDC25 "Meet the Foundation Models framework"](https://developer.apple.com/videos/play/wwdc2025/286/)
- [docs] Context window: 4,096 tokens per `LanguageModelSession`, input and output together; an Apple engineer says this may change across releases or devices — [TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window); [Apple Developer Forums 790736](https://developer.apple.com/forums/thread/790736)
- [press] iOS 26.4 added `contextSize` on `SystemLanguageModel` and `tokenCount(for:)` so apps can budget at runtime — [InfoQ, March 2026](https://infoq.com/news/2026/03/apple-foundation-models-context)
- [vendor claim] Apple's 2025 tech report says the on-device model matches or beats comparably sized open models on benchmarks and human evaluation; InfoQ reports it compares well against Qwen-2.5-3B — [Apple ML Research tech report 2025](https://machinelearning.apple.com/research/apple-foundation-models-tech-report-2025); [InfoQ, July 2025](https://www.infoq.com/news/2025/07/apple-foundation-models-ios26)

**NLTokenizer and dictation**
- [docs] `NLTokenizer` takes an `NLTokenUnit` of `.word`, `.sentence`, `.paragraph` or `.document` (macOS 10.14+). Note: the page body did not render in my fetch; the case list is from prior knowledge of the API — [Apple NLTokenUnit](https://developer.apple.com/documentation/naturallanguage/nltokenunit)
- [docs] macOS Dictation formatting commands include "new line" and "new paragraph"; for supported languages Dictation inserts some punctuation automatically — [Apple Mac User Guide: dictation commands](https://support.apple.com/guide/mac-help/mh40695/mac); toggle in Keyboard > Dictation settings — [MacMost](https://macmost.com/how-to-use-dictation-on-your-mac-2.html)
- [review] Automatic punctuation is inconsistent: it added a comma after "however" but missed a sentence end — [TWiT Hands-On Mac 183 transcript](https://twit.tv/posts/transcripts/hands-mac-183-transcript)

### Inferences
- NSSpellChecker is the cheapest offline option that covers many languages and respects the user's own text replacements, but expect spelling and autocorrect only; grammar from a custom view is unproven and should be treated as absent until tested.
- A tool drawing its own text (not an NSTextView, e.g. a Rust/GPUI canvas) can get panel-style Writing Tools by adopting `NSServicesMenuRequestor`. Inline proofreading marks need the coordinator, whose delegate must produce attributed-string contexts, per-range bezier paths and preview images: large cost for a minimal tool, plus the reported Replace/`insertText:` bug.
- Writing Tools cannot be promised as on-device: Apple's own example routes proofreading to PCC. For a "nothing leaves the Mac" promise it does not qualify, though PCC's no-retention claims may satisfy many users.
- Foundation Models budget for proofreading: output ≈ input length for a full corrected copy, so 4,096 tokens allow roughly 1,500–1,800 input tokens after instructions, i.e. about 1,000–1,300 English words per session at ~1.3–1.5 tokens/word (estimate). Paragraph-by-paragraph sessions fit easily. Guided generation could return a structured edit list (original span, replacement, category) instead of a full rewrite, which shortens output and makes per-change review natural.
- Foundation Models is Swift-only; a Rust tool needs a small Swift shim (static library or helper process). No source checked for this; it is an inference from the API being Swift.
- `NLTokenizer(.paragraph)` splits on existing line breaks, so it cannot invent paragraph breaks in a run-on block; `.sentence` helps only where terminal punctuation exists. Useful for chunking for an LLM, not for repair.

### Gaps
- Exact minimum macOS for `NSWritingToolsCoordinator` (the brief says 15.2; the doc page body did not render). Whether `showWritingTools(_:)` exists as public AppKit API was not confirmed.
- No measured latency for Writing Tools Proofread or for Foundation Models generation on specific Macs.
- No published evaluation of the Foundation Models on-device model for proofreading or grammatical error correction.
- Whether a user or app can force Writing Tools to stay on device (no PCC) was not found.
- Which languages NSSpellChecker's grammar checker covers, and how many spelling dictionaries ship, was not found.

## 2. Open-source offline checkers: Harper, LanguageTool, nlprule, Vale, hunspell

### Takeaway
Harper is the obvious embeddable candidate for a Rust tool (Apache-2.0 `harper-core` crate, offline, claimed <10 ms), but it is English-only and independent reviewers find it catches fewer errors than LanguageTool. LanguageTool has the broadest coverage (30+ languages) but means running a Java server with optional multi-GB n-gram data, and its premium rules are not in the open-source build. nlprule ports ~85–90% of LanguageTool 5.2's rules to Rust for English and German. Vale is a style linter, not a typo or grammar fixer. No formal accuracy benchmark comparing these tools was found.

### Cited Findings
- [vendor claim] Harper: offline, English grammar checker in Rust; "milliseconds to lint a document"; under 1/50th of LanguageTool's memory; author calls LanguageTool slow ("several seconds on moderate-sized documents") and heavy (~16 GB n-gram dataset); Apache-2.0; repository at Automattic — [GitHub Automattic/harper](https://github.com/Automattic/harper)
- [vendor claim] Harper site: English dialects (American, British, Canadian, Australian, Indian); "Suggestions in under 10ms"; no cloud, telemetry or LLM; catches spelling, grammar/awkward phrasing, capitalization (punctuation not listed); integrations include **Harper Desktop, a system-wide macOS app for any text field**, Chrome/Edge/Firefox, VS Code, Neovim, Zed, Obsidian, WordPress, `harper-ls`, `harper.js`, and the **`harper-core` Rust crate** — [writewithharper.com](https://writewithharper.com/)
- [docs] Harper 2.10.0 (October 2026) still states it "currently only supports English, but the core is extensible" — [Chocolatey package listing](https://community.chocolatey.org/packages/harper)
- [review] It's FOSS: Harper missed a deliberately misspelled "videoin", showed about three suggestions at a time; reviewer had no data to confirm the speed claims — [It's FOSS](https://itsfoss.com/harper-grammar-checker/). A Lemmy user: Harper covers "way fewer rules" than LanguageTool and lacks many style suggestions — [Lemmy thread](https://lemmy.imagisphe.re/post/1581549/4338010)
- [docs] nlprule: Rust, rule- and lookup-based using LanguageTool resources; English (all 843 disambiguation rules, ~85% of 3,725 grammar rules of LanguageTool 5.2), German (~90% of 2,970), Spanish experimental; benchmark shows nlprule at relative time 1 vs LanguageTool 1.7–2.0 (English) and 2.4–2.8 (German); code MIT/Apache-2.0, bundled binaries LGPL-2.1 (derived from LanguageTool 5.2); `rules.correct(text, &tokenizer)` returns a corrected string — [GitHub bminixhofer/nlprule](https://github.com/bminixhofer/nlprule)
- [review/3rd party] LanguageTool self-host: premium-only rules and AI rewriting are not in the open-source build; self-hosted premium only for commercial use by quote — [credativ](https://www.credativ.de/en/blog/credativ-inside/languagetool-powerful-language-checking-on-your-own-network/); n-gram data is an optional multi-GB download — [AWS Marketplace listing](https://aws.amazon.com/marketplace/pp/prodview-awhaoi5wgcnn4); a setup guide suggests ~20 GB free storage for n-grams — [dev.to guide](https://www.dev.to/dacbreakpoint/setup-your-private-languagetool-server-4l9o); n-grams improve confusion detection such as their/there — [DINAO](https://dinao.com/en/conteneur/languagetool)
- [docs] Vale: command-line prose linter in Go; "focuses (primarily) on the style of writing rather than its grammatical correctness"; rules are YAML "styles"; Markdown-aware (code ignored by default); MIT — [Vale docs](https://docs.vale.sh/)

### Inferences
- For a forward-only English draft, Harper fixes the "cheap" class (misspellings, a/an, capitalization, repeated words) offline and fast, and the crate drops into a Rust codebase without a server. It will not restore missing sentence punctuation or paragraphing; nothing rule-based reliably does.
- Harper Desktop already works system-wide on macOS, so a user who pastes the raw draft into their usual editor gets Harper checking without the flow tool integrating anything. Same for NSSpellChecker in any NSTextView and for Writing Tools.
- LanguageTool is the multilingual answer but too heavy to bundle in a minimal tool; reasonable only as "if the user already runs a LanguageTool server, point at it".
- nlprule is attractive for German, but it is pinned to LanguageTool 5.2 resources and its binaries are LGPL; maintenance status could not be confirmed.
- Vale is not relevant for typo/punctuation repair.

### Gaps
- No independent precision/recall comparison of Harper, LanguageTool and nlprule on the same error set was found.
- No measured Harper latency on a 2,000-word document from an independent source.
- hunspell/enchant were not researched in depth (no sources fetched); they provide spelling only.
- nlprule's last release date and maintenance status were not visible on the repository page.

## 3. Local LLMs (MLX, llama.cpp, Ollama) for "fix typos and punctuation, do not change wording"

### Takeaway
A local 3–8B model can restore punctuation and fix typos that rule-based tools miss, fully offline, but research shows small models struggle to keep meaning and hallucinate, and even large LLMs "systematically overcorrect" unless constrained. Latency is dominated by output tokens: a full corrected copy of 1,000 words takes roughly 20 s to 2 min with a 7B model depending on the chip (estimated from measured llama.cpp throughput), so the output format (edit list vs full copy) and background processing matter more than model choice. Every credible design pairs the model with a diff and per-change acceptance.

### Cited Findings
- [measured] llama.cpp community benchmark, Llama 2 7B Q4_0 (prompt processing pp512 / generation tg128, tokens/s): M1 8-GPU 118 / 14.2; M2 10-GPU 180 / 21.9; M3 10-GPU 187 / 21.3; M4 10-GPU 221 / 24.1; M4 Pro 20-GPU 440 / 50.7; M4 Max 40-GPU 886 / 83.1; M5 Pro 20-GPU 1,621 / 66.3; M5 Max 40-GPU 3,220 / 119.9 — [llama.cpp discussion #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)
- [estimate, not measured] LLMCheck lists ~118 tok/s generation for Qwen 3 4B Q4_K_M and ~95 tok/s for Gemma 3 4B Q8_0 on an M4 Pro via MLX, derived from memory-bandwidth scaling — [LLMCheck Qwen 3 4B](https://llmcheck.net/models/qwen-3-4b-on-m4-pro/); [LLMCheck Gemma 3 4B](https://llmcheck.net/models/gemma-3-4b-on-m4-pro/)
- [measured] Dedicated small proofreading model: Google's MediaPipe Text Proofreader, 200M parameters, fixes spelling, grammar and style, returns insertions/deletions breakdown; end-to-end on a Pixel 10 Pro CPU: 100 words 0.98 s, 500 words 4.9 s, 1,000 words 16 s, 2,000 words 28 s; 200–350 MB peak memory; Gemma terms; guides for Android, iOS, Python (macOS not listed) — [Google MediaPipe Text Proofreader](https://developers.google.com/edge/mediapipe/solutions/text/text_proofreader)
- [paper] Gboard "Proofread" (server-side PaLM2-XS) reached 85.56% "good ratio" on a human-labelled set — [arXiv 2406.04523](https://arxiv.org/html/2406.04523v1)
- [paper] Small decoder-only models (out of the box, fine-tuned, sequential) on JFLEG: performance "remains below strong baselines and current LLMs"; "SLMs struggle with retaining meaning and hallucinations"; "not yet competitive enough with modern LLMs for rewriting" (Lamelas, January 2026) — [arXiv 2601.03874](https://arxiv.org/abs/2601.03874)
- [paper] Fine-tuned minimal-edit open models on BEA-2019 test (F0.5): Mistral-7B 75.91, Gemma 2 9B 77.41, Llama-2-13B 72.69, Gemma 2 27B 78.70 — these are fine-tuned GEC models, not prompted chat models — [arXiv 2506.13148](https://arxiv.org/pdf/2506.13148)
- [paper] Prompted LLMs "systematically overcorrect and degrade F0.5 by rewriting well-formed spans"; adding a taxonomy of allowed error types bounds edits (helps strongest models most); batching several sentences per input "acts as a targeted regularizer against overcorrection"; best prompted result Gemini 3.1-Pro F0.5 78.32 on BEA-2019, 0.38 behind fine-tuned SOTA (Karpo & Chernodub, EMNLP 2026 Findings) — [arXiv 2609.10810](https://arxiv.org/abs/2609.10810)
- [paper] Minimal-edit prompting lifted GPT-4.1-mini from 47.97 to 54.84 on Ukrainian GEC; GPT-5.4 gained only ~1.4 points — [arXiv 2606.09334](https://arxiv.org/pdf/2606.09334)
- [review] Diff-based acceptance UIs that exist: Obsidian "Proofreader" plugin highlights additions and strikes deletions, accept/reject via hotkeys (needs an OpenAI key) — [Obsidian community plugin](https://community.obsidian.md/plugins/proofreader); a Go terminal "proofread" tool works with local Ollama but just replaces the text and underlines changed words until you type — [pkg.go.dev StevenCyb/proofread](https://pkg.go.dev/github.com/StevenCyb/proofread); Tiptap's AI toolkit proofreader offers suggestions with reject-all — [Tiptap docs](https://tiptap.dev/docs/content-ai/capabilities/ai-toolkit/workflows/proofreader); Dr. Drang reviews Writing Tools' output with a two-pane diff and edits differences in place — [leancrew.com](https://leancrew.com/all-this/2026/01/proofreading-with-writing-tools/)
- [docs] Superwhisper warns that custom prompts can cause hallucinations and that local models "have more limited capabilities and need more specific prompting" — [Superwhisper hallucinations](https://ai.superwhisper.com/docs/common-issues/hallucinations)

### Inferences
- Latency estimate for a full corrected copy, 7B Q4 model, 1,000 words (~1,500 input + ~1,500 output tokens), from the measured table: M1 ≈ 13 s prefill + 106 s decode ≈ 2 min; M4 ≈ 7 s + 62 s ≈ 70 s; M4 Pro ≈ 3 s + 30 s ≈ 33 s; M4 Max ≈ 2 s + 18 s ≈ 20 s; M5 Max ≈ 13 s. A 3–4B model should be roughly 1.5–2× faster (decode is memory-bound). Scale linearly for 500 or 2,000 words.
- Asking for an **edit list** (only changed spans, e.g. 30 fixes ≈ 150–300 output tokens) instead of a full copy cuts decode time about 5–10×: a few seconds on an M4 Pro even with a 7B model. It also makes per-change acceptance trivial and makes silent rewrites of untouched spans impossible (anything not in the list is unchanged by construction). Validation is cheap: reject any edit whose "original" span is not found verbatim, and any edit that changes more than N characters or touches content words beyond an edit-distance threshold.
- Mitigations that the evidence supports: (1) a closed list of allowed edit categories (spelling, punctuation, capitalization, spacing, paragraph break) per the taxonomy result; (2) whole paragraphs or several sentences per call rather than single sentences (batching reduces overcorrection); (3) a deterministic guard that flags edits removing negations ("not", "never") or numbers, given the Wispr Flow failure reports (section 6); (4) diff with per-change accept and "accept all mechanical".
- Model download is several GB for a 4–8B model (inference from quantized sizes; not sourced), a real cost for a "minimal" tool. Foundation Models avoids the download on Macs with Apple Intelligence enabled.
- A dedicated small GEC model (MediaPipe's 200M) shows the "right-sized" approach exists, but it is not packaged for macOS; using it would mean converting the model, which is speculative.

### Gaps
- No measured benchmark of Qwen3, Gemma 3n, Phi-4-mini or Llama 3.2 on a proofreading task (accuracy or meaning-preservation rate) on Apple Silicon was found.
- No measured llama.cpp prefill/decode numbers for 3–4B models across M-series chips in one consistent table; the 4B figures found are estimates.
- No study measuring how often small models make meaning-changing edits under a minimal-edit prompt with an edit-list output.

## 4. Cloud LLMs (Claude, OpenAI, Gemini) for proofreading; user attitudes

### Takeaway
Cloud models give the best correction quality per the GEC literature but still overcorrect without minimal-edit constraints; cost is negligible (about $0.001–0.04 per 1,000 words at current Claude prices), and the decisive factor is privacy: the draft leaves the Mac. Writers are split: many professionals use AI to polish, fiction authors are warier, and a majority in one 2026 survey distrust AI-supported writing even of their own words.

### Cited Findings
- [docs] Claude API prices per million tokens (input / output): Haiku 5.5 $0.10 / $0.50 (prompts ≤100k tokens); Haiku 4.5 $1 / $5; Sonnet 5.5 $2 / $10; Opus 5.5 $4 / $20; Batch API 50% off; Claude 4.7+ use a newer tokenizer producing ~30% more tokens for the same text — [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- [3rd party, conflicting] OpenAI: GPT-5 mini $0.25 / $2.00 and GPT-5 nano $0.05 / $0.40 per MTok per one aggregator — [AnotherWrapper](https://anotherwrapper.com/llm-pricing/gpt-5-mini-2025-08-07); a June 2026 guide lists GPT-5.4-mini $0.75 / $4.50 and GPT-5.4-nano $0.20 / $1.25 — [MorphLLM](https://morphllm.com/openai-api-pricing). Not verified on openai.com.
- [paper] ChatGPT is "not particularly inclined to use minimal edits, especially in short sentences", more conservative as sentences get longer — [arXiv 2304.01746](https://arxiv.org/pdf/2304.01746)
- [paper] GPT-4 on Brazilian Portuguese: high recall, lower precision; "they tend to make more corrections than necessary, potentially altering the meaning or style", though it had the best F0.5 for grammar and spelling among methods tested — [arXiv 2306.15788](https://arxiv.org/pdf/2306.15788)
- [paper] Best prompted system (Gemini 3.1-Pro with taxonomy instructions and batching) F0.5 78.32 on BEA-2019 — [arXiv 2609.10810](https://arxiv.org/abs/2609.10810)
- [survey] Gotham Ghostwriters / Josh Bernoff, 1,481 writers (2025): 61% of writing professionals use AI at least sometimes, 26% daily; fiction authors "much more wary"; favourability rises with use — [AI Writer Survey PDF](https://gothamghostwriters.com/wp-content/uploads/2025/11/AI-Writer-Survey.pdf); [Publishers Weekly](https://www.publishersweekly.com/pw/print/20251110/99019-new-report-examines-writers-attitudes-toward-ai.html)
- [survey] Medium report (2026): 33% use AI tools to edit for grammar, clarity or tone; 60% feel distrustful toward AI-supported writing, including their own — [GamesBeat on the Medium report](https://gamesbeat.com/?p=335175)

### Inferences
- Cost per 1,000 words for a full corrected copy (~2,000 input tokens incl. instructions, ~1,700 output, newer tokenizer): Haiku 5.5 ≈ $0.001; Haiku 4.5 ≈ $0.01; Sonnet 5.5 ≈ $0.02; Opus 5.5 ≈ $0.04; GPT-5 mini ≈ $0.004 (if the aggregator price holds). Edit-list output cuts this further. Cost is not a design constraint; an API key, network and privacy are.
- Latency for cloud is dominated by output tokens too; an edit-list format keeps it to a few seconds. No measured figure was gathered.
- Because one survey reports 60% distrust even of their own AI-assisted text, an AI pass that is opt-in, visible and reversible is the only version that fits a writer-facing tool; a default-on cloud pass would contradict a forward-only tool's appeal (privacy, ownership of words).

### Gaps
- Gemini pricing and current official OpenAI pricing were not verified.
- No measured end-to-end cloud latency for a 1,000-word proofread.
- No head-to-head study of cloud vs local small models on proofreading of raw, unpunctuated freewriting (the GEC benchmarks use learner essays, which differ).
- Reddit r/writing and r/macapps threads on AI proofreading were not fetched; a BookBub (May 2025) author-survey figure (≈45% use AI, 70% of those for editing) appeared in search snippets but could not be tied to a fetched source.

## 5. Formatting inference without AI: pauses, Enter conventions, spoken markers, dictation-style capitalization

### Takeaway
Writing research confirms writers pause longer at sentence and paragraph boundaries, but the pauses do not follow one distribution, so a fixed timing threshold would mis-place breaks; no product was found that inserts paragraph breaks from typing pauses. The robust non-AI options are explicit: Return (once or twice) as paragraph mark, dictation-style commands, and deterministic clean-up (sentence capitalization, spacing, "i" → "I") that needs no model.

### Cited Findings
- [paper] Keystroke-logging study (Inputlog, 25 postgraduates, 3 essays each): students paused over sentence and paragraph boundaries; between-paragraph pauses were higher in narrative than argumentative essays at shorter thresholds — [Mohsen 2021, Psycholinguistics](https://psycholing-journal.com/index.php/journal/article/view/1213)
- [paper] Keystroke logs from 32 students: transitions at sentence, sub-sentence, word and within-word boundaries "cannot be characterised by a single distribution" of cognitive pauses — [University of Southampton ePrints 457616](https://eprints.soton.ac.uk/457616)
- [review] Freewrite Traveler lets the writer move the cursor (WASD with a modifier) to fix earlier text; no copy/paste — [TechCrunch review](https://techcrunch.com/2020/10/27/the-freewrite-traveler-is-an-outstanding-but-expensive-dedicated-portable-writing-laptop). No pause-to-paragraph feature was found.
- [review] ilys shows only the last character typed, text invisible until the writer finishes, no delete or edit — [The Next Web](https://thenextweb.com/news/write-drunk-edit-sober); [Reedsy directory](https://reedsy.com/resources/writing-apps/book/page/5). WriteForward hides previous paragraphs as you write — [AlternativeTo](https://alternativeto.net/software/writeforward/about)
- [docs] macOS Dictation uses spoken "new line" / "new paragraph" commands and adds some punctuation automatically in supported languages — [Apple Mac User Guide](https://support.apple.com/guide/mac-help/mh40695/mac); auto-punctuation reported inconsistent — [TWiT transcript](https://twit.tv/posts/transcripts/hands-mac-183-transcript)

### Inferences
- Pause timing is better used as a *hint* (e.g. a candidate break shown in the end-of-session review) than as an automatic break. Pause data is free to record during the session and could also feed an LLM prompt ("pauses > Xs occurred here") — speculative, untested.
- Plain Return remains available even in a forward-only flow (it moves forward); Return as paragraph break is the cheapest and most predictable convention, and it is also what makes `NLTokenizer(.paragraph)` and Markdown output work.
- Deterministic clean-up worth doing with no model: capitalize after `.?!` + space and at paragraph start, collapse double spaces, remove space before `,.;:?!`, "i" → "I" as a word, curly quotes/dashes if desired. These are reversible, predictable and safe to apply without review. They cannot add missing full stops in run-on text; that needs a model.
- Markdown as output format fits: paragraphs separated by blank lines, nothing else assumed.

### Gaps
- No product found that infers paragraphs from typing pauses (Freewrite, ilys, WriteForward searched); absence is not proof.
- No published pause thresholds usable as defaults (full texts of the keystroke studies not read).
- How Wispr Flow, Superwhisper and VoiceInk add capitalization and punctuation internally (rules vs LLM) beyond "Smart Formatting"/modes was not documented in sources found.

## 6. Dictation apps: how Wispr Flow, Superwhisper and VoiceInk "clean up", and what reaches the focused app

### Takeaway
Dictation apps clean up *before* inserting into the focused app, with an LLM, and that silent clean-up is exactly where their worst complaints come from: Wispr Flow's Auto Cleanup dropped words like "not" and "never" and changed meaning, and Wispr's own docs admit the step judges filler vs content without fixed rules. Wispr runs formatting in the cloud; Superwhisper and VoiceInk let the user choose local or cloud models per mode.

### Cited Findings
- [docs] Wispr Flow's Smart Formatting "judges what is conversational filler and what is intended content rather than following a fixed list of rules, so it can drop or rewrite words that mattered"; examples: a leading "so" with conditional meaning dropped, deliberate repetition removed, "one point something percent" collapsed to "1%"; more aggressive on conversational English; same logic on Mac, Windows, iOS — [Wispr Flow help article](https://docs.wisprflow.ai/articles/6568835559-why-wispr-flow-sometimes-removes-or-changes-words-on-android-smart-formatting)
- [press] Wispr asked its detractors what was wrong (700+ answered) and traced some accuracy problems to an overly aggressive Auto Cleanup that changed words users had not asked it to touch; says it corrected this — [Digital Trends](https://www.digitaltrends.com/computing/wispr-flow-asked-its-haters-what-was-wrong-and-more-than-700-people-answered/)
- [review] A user dictating because of a hand injury reports the tool regularly removes "not", "never", "before", e.g. turning "never merge a change like this" into "merge a change like this" (single report) — [Digg summary](https://digg.com/ai/ve5pkh0s); a G2 reviewer says it sometimes treats meaningful words as filler — [G2 review](https://www.g2.com/survey_responses/wispr-flow-review-13781077)
- [competitor claim] Wispr Flow's reformatting runs on cloud models; Privacy Mode (off by default for consumers) adds zero-data-retention with its LLM providers but does not keep data on the Mac — [Yaps.ai, a competing app](https://www.yaps.ai/blog/is-wispr-flow-safe)
- [docs] Superwhisper modes each pick a voice model and an AI model with a custom prompt — [Superwhisper modes](https://superwhisper.com/docs/modes); a local speech model with a cloud LLM mode sends the text to that provider — [Laxis review](https://www.laxis.com/blog/superwhisper/); changelog 2.11–2.12 adds automatic filler-word removal and stripping of stray "think" output from LLMs — [Superwhisper changelog](https://superwhisper.com/changelog)
- [docs] VoiceInk: GPL-3.0, macOS 15+, local transcription, "Modes" applied per app or URL — [GitHub Beingpax/VoiceInk](https://github.com/Beingpax/VoiceInk); its AI clean-up can run locally (Ollama) — [Lumevoice comparison](https://lumevoice.com/blog/voiceink-vs-superwhisper/) (a competitor's comparison)

### Inferences
- What the dictation category teaches: (1) users want the raw output cleaned before it lands, (2) silent LLM clean-up produces rare but severe meaning changes, which users only notice after the fact, (3) vendors respond by making the step less aggressive. For a writing tool, where the words are the product, the same failure is worse than in dictation.
- If the flow tool types or pastes raw text straight into the focused app, the clean-up opportunity is lost to the tool; the target app's own checkers (NSTextView spelling, Writing Tools, Harper Desktop) then become the post-processor. That is a legitimate design (hand-off), not a gap.
- How dictation apps insert text (clipboard paste plus synthetic ⌘V vs accessibility APIs) was not confirmed in sources; it matters only if the tool also inserts into other apps.

### Gaps
- No quantitative error-rate data for any dictation app's clean-up.
- Superwhisper's local-LLM options and VoiceInk's AI enhancement providers were described only by third-party or competitor pages.

## 7. Workflow designs (a)–(d), what comparable tools choose, and the evaluated menu

### Takeaway
Forward-only writing tools ship no post-processing (raw text out); dictation apps clean silently before paste and pay for it in trust; editors hand off to system Writing Tools and review with a diff. The evidence favours: deterministic mechanical clean-up that is always safe, plus an optional, visible end-of-session pass (local or Apple model, edit-list output, per-change diff). Continuous background *correction* of text the writer cannot see conflicts with documented trust problems; background *computation of suggestions*, shown only at the end, keeps the latency benefit without the trust cost. Keeping AI out of the tool entirely is credible because the Mac already provides Writing Tools, Shortcuts actions and Harper Desktop in the user's own editor.

### Cited Findings
- [review] Write-forward tools (ilys, WriteForward) hide text and are described without any clean-up stage — [The Next Web](https://thenextweb.com/news/write-drunk-edit-sober); [AlternativeTo](https://alternativeto.net/software/writeforward/about)
- [docs/review] Dictation apps clean before insertion (Wispr Smart Formatting, Superwhisper and VoiceInk modes) and have documented meaning-changing failures — [Wispr Flow help](https://docs.wisprflow.ai/articles/6568835559-why-wispr-flow-sometimes-removes-or-changes-words-on-android-smart-formatting); [Digital Trends](https://www.digitaltrends.com/computing/wispr-flow-asked-its-haters-what-was-wrong-and-more-than-700-people-answered/)
- [review] Apple's Writing Tools review was criticised as all-or-nothing and not showing what changed; a power user adds his own diff step to review it — [Android Authority](https://www.androidauthority.com/apple-intelligence-vs-grammarly-feature-3466509); [AppleInsider](https://appleinsider.com/inside/ios-18/vs/apple-intelligence-vs-grammarly----ai-powered-text-tool-showdown); [leancrew.com](https://leancrew.com/all-this/2026/01/proofreading-with-writing-tools/)
- [docs] macOS 26 adds Proofread/Rewrite/Summarize Shortcuts actions; any view adopting `NSServicesMenuRequestor` gets basic Writing Tools — [WWDC25 session 265](https://developer.apple.com/videos/play/wwdc2025/265/)
- [vendor claim] Harper Desktop checks any text field system-wide on macOS, offline — [writewithharper.com](https://writewithharper.com/)
- [survey] 60% of Medium survey respondents distrust AI-supported writing, including their own — [GamesBeat](https://gamesbeat.com/?p=335175)

- On (c) trust: correcting text the writer cannot see is defensible only for P1-class mechanical fixes (deterministic, explainable, reversible). For anything model-made, the evidence (Wispr's meaning-changing drops, criticism of Apple's all-or-nothing review, 60% distrust) says changes must be visible and individually reversible. P9′ is the version that keeps the flow undisturbed and the writer in control.
- On "in the tool or a separate tool": P0 + P1 keeps the tool minimal and still yields clean paragraphs and casing; the user's editor then supplies spelling/grammar (NSSpellChecker, Writing Tools, Harper Desktop) without the tool owning any AI. P5 via a Services or Shortcuts hand-off adds AI with almost no code but cannot promise on-device. An in-tool AI pass (P6/P7/P8) is justified only if a measured test on real forward-only drafts shows it fixes what the hand-off misses (mostly missing sentence punctuation and run-ons) without meaning changes.
- The strongest cheap path to evaluate first: P1 always, P3 (if English is enough) as an end-of-session review, and P5 as an optional hand-off. A local-model pass should use edit-list output, a closed set of edit categories, paragraph-sized batches and a negation/number guard, and should be built only after a test on a handful of real drafts.
- A test protocol that settles the open quality questions cheaply: take 5–10 real forward-only drafts (500–2,000 words), run P3, P5, P6 and one P7 model, count per draft: true fixes, missed errors, and meaning-changing edits (any changed content word, dropped negation or number). That number, not vendor claims, should decide whether AI belongs in the tool.

### Gaps
- No comparable forward-only writing tool documents a post-processing design or its rationale; the "what they choose and why" answer rests on absence of features plus dictation-app evidence.
- No user study on whether writers accept invisible background correction in a forward-only tool.
- No measured comparison of Writing Tools, Foundation Models and local LLMs on the same raw freewriting text.
