# macOS implementation technology for a small, very responsive writing app (state: October 2026)

Scope: framework/language choice, keystroke sound, text injection into the frontmost app, dimming the rest of the screen, hotkey/panel summoning, smooth 120 Hz horizontal text scroll, later cross-platform reach. The implementer knows Rust and GPUI well, Swift less.

Note on sources: several GPUI facts below were read directly from the GPUI source published on crates.io (`gpui-pre` 0.3.8 family, a snapshot of Zed's `crates/gpui`), cached locally; the docs.rs source URLs given point at the same files. "Local measurement" marks a number measured on the research machine, with no URL.

## Frameworks: which stack gives the shortest key-to-paint path, correct macOS text input (IME, marked text, dead keys, Option characters), 120 Hz, small size and good OS integration?

### Takeaway
Only stacks that route keys through AppKit's `interpretKeyEvents:` into a proper `NSTextInputClient` get dead keys, Option characters and CJK input right; native AppKit does by definition, GPUI does (Zed's own implementation, actively fixed in 2026), WKWebView-based Tauri mostly does, while winit-based stacks (egui, iced, raw winit+wgpu) still have open dead-key bugs on macOS. GPUI is the strongest Rust option (Metal, CVDisplayLink pacing, Core Text shaping, 120 Hz proven in Zed, non-activating NSPanel built in, AccessKit accessibility), but is pre-1.0 and gives no menu-bar/status-item API; Swift+AppKit is the lowest-risk, smallest macOS-only route; Flutter, Tauri and Electron add size or text-input risk without a benefit for this app.

### Cited Findings

**Text input correctness (IME, dead keys, Option characters)**
- Apple defines `NSTextInputClient` as "a set of methods that text views need to implement to interact properly with the text input management system" — [Apple: NSTextInputClient](https://developer.apple.com/documentation/appkit/nstextinputclient)
- On macOS a dead-key sequence (e.g. ⌥E then E → é) is handled as IME composition (marked text), unlike Windows where it is two key events — [W3C public-webapps-github, Masayuki Nakano, 2023](https://lists.w3.org/Archives/Public/public-webapps-github/2023Jul/0056.html)

**Rendering, frame pacing, 120 Hz**
- GPUI macOS text system uses Core Text for shaping (`CTLine`, font-kit loaders over Core Text), grayscale AA rasterization with subpixel positioning enabled (`set_should_subpixel_position_fonts(true)`, quantization off) and `SUBPIXEL_VARIANTS_X = 4`, `SUBPIXEL_VARIANTS_Y = 1` — [gpui-pre-macos 0.3.8 src/text_system.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/text_system.rs); [gpui-pre 0.3.8 src/text_system.rs](https://docs.rs/crate/gpui-pre/0.3.8/source/src/text_system.rs) (read locally)
- GPUI paces frames with one immortal `CVDisplayLink` per display in a static registry that windows subscribe to (to avoid CVDisplayLink teardown crashes seen in Zed) — [gpui-pre-macos 0.3.8 src/display_link.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/display_link.rs) (read locally)
- `CVDisplayLinkCreateWithActiveCGDisplays` is deprecated (availability macOS 10.4–15.0); replacements are `NSView/NSWindow/NSScreen.displayLink(target:selector:)`, which return a `CADisplayLink` — [Apple doc](https://developer.apple.com/documentation/corevideo/cvdisplaylinkcreatewithactivecgdisplays(_:)); [QEMU issue 2575](https://gitlab.com/qemu-project/qemu/-/issues/2575); [Apple forums 791564 (DTS recommends CADisplayLink / CAMetalDisplayLink)](https://developer.apple.com/forums/thread/791564)
- `NSView.displayLink(target:selector:)` is macOS 14.0+; `CADisplayLink.preferredFrameRateRange` is macOS 14.0+ — [Apple: displayLink(target:selector:)](https://developer.apple.com/documentation/appkit/nsview/displaylink(target:selector:)); [Apple: preferredFrameRateRange](https://developer.apple.com/documentation/quartzcore/cadisplaylink/preferredframeraterange)
- Zed's 120 fps work (Feb 2024): GPUI frame times were "consistently under 4 ms" but frames still dropped because ProMotion downclocked the display; fix: present a frame on every display-link callback for one second after the last input event; result "a smooth 120 fps" with 10 ms key repeat on an M1 MacBook Pro. A later fix removed `presentsWithTransaction`/`wait_until_scheduled` and called `present_drawable` before `commit()` for stable 120 fps (CVDisplayLink alone oscillated 8–16 ms frame times); `presentsWithTransaction` kept only for startup/resize; triple-buffered instance buffers — [Zed blog: Optimizing the Metal pipeline to maintain 120 FPS in GPUI](https://zed.dev/blog/120fps)
- One 120 Hz frame is 8.3 ms — [BenQ FAQ (via search)](https://benq.com/en-hk/support/downloads-faq/faq/product/specification/projector-faq-kn-00074.html)

- Electron is ruled out by size alone (80–150 MB for a hello-world against a "tiny, instant" goal) and adds a JS/compositor hop; Tauri is small but puts a web engine and JS between the keystroke and the paint, and its IME bugs sit in the Rust host layer (tao/wry) that the implementer cannot easily avoid.
- egui/iced/raw winit fail the hard requirement: a writing app must handle ´+e=é and ⌥ characters; their macOS dead-key issues have been open for years. A winit-based custom stack would have to patch winit's macOS view or bypass it with its own `NSView`.
- GPUI is the only Rust option whose macOS text input is maintained by a team shipping a text editor to an international user base; expect occasional IME edge-case regressions on snapshot bumps (pin a version, test ⌥E E, ⌥U U, ⌥N N, Pinyin, Japanese Kana before each bump).
- What the Swift route would cost the implementer: learning AppKit's responder chain, `NSTextInputClient`, Core Animation and Swift concurrency; a single-line custom text view with IME is a few hundred lines; the OS-integration code (CGEvent, AX, AVAudioEngine, NSPanel, overlays) is the same either way and is most natural in Swift. Payback: smallest binary, zero framework risk, first-class accessibility. Loss: a full UI rewrite for Windows/Linux.

## Sound: lowest-latency typewriter/mechanical click on each keystroke with per-key variation, from Swift and from Rust; samples and licences; capturing keys

### Takeaway
Play clicks from your own always-running output stream: preload every sample as PCM in memory, keep the engine/stream running (never start/connect per click), mix voices in the render callback, and shrink the device I/O buffer (CoreAudio's default is 512 frames ≈ 10.7 ms at 48 kHz; buffers can be requested down to ~32–128 frames). In Swift that is AVAudioEngine with pre-attached `AVAudioPlayerNode`s + `scheduleBuffer`, or an `AVAudioSourceNode`; in Rust it is a cpal stream (CoreAudio DefaultOutput AudioUnit) with a hand-written mixer, or kira on top of cpal. Do not use `AVAudioPlayer` per keystroke or effect units like TimePitch. Bluetooth headphones add 120–300 ms that no code can remove. Keystrokes typed into the app's own window need no permission.

### Cited Findings
- Apple TN2321: legal I/O buffer frame sizes come from `kAudioDevicePropertyBufferFrameSizeRange`; the default I/O buffer is 512 sample frames, and setting the power hint `kAudioHardwarePowerHintFavorSavingPower` raises it to 4096 frames (OS X 10.9+) — [Apple TN2321](https://developer.apple.com/library/mac/technotes/tn2321/_index.html)
- CoreAudio reportedly does not go below 32 frames per buffer for apps; requested sizes can be rounded (JUCE users saw multiples of 32) — [Gearspace: macOS Core Audio mysteries](https://gearspace.com/threads/macos-core-audio-mysteries.1453740/); [JUCE forum](https://forum.juce.com/t/getting-real-buffer-sizes-from-a-device-on-macos/66844)
- AVAudioNode `latency`/`presentationLatency` often report 0.0 on macOS; query `kAudioDevicePropertyLatency`, `kAudioDevicePropertyBufferSize`, `kAudioDevicePropertySafetyOffset` instead; one developer saw ≈720-sample offsets on his Mac and up to 1500 on others — [Stack Overflow 65600996 (mirror)](https://dev.library.kiwix.org/content/stackoverflow_en_nopic_2021-08/questions/65600996/avaudioengine-reconcile-sync-input-output-timestamps-on-macos-ios); [Apple: presentationLatency](https://developer.apple.com/documentation/avfaudio/avaudioionode/presentationlatency)
- `AVAudioPlayerNode.scheduleBuffer(_:at:options:completionHandler:)` schedules an `AVAudioPCMBuffer`; `AVAudioSourceNode` (macOS 10.15+/iOS 13+) supplies audio from a render block instead of an AU render callback — [Apple: scheduleBuffer](https://developer.apple.com/documentation/avfaudio/avaudioplayernode/schedulebuffer(_:at:options:completionhandler:)); [Apple: AVAudioSourceNode](https://developer.apple.com/documentation/avfaudio/avaudiosourcenode)
- A developer saw `AVAudioPlayerNode.play()` take close to 20 ms when reconnecting nodes per play; pre-connected nodes avoid this — [Apple forums 68603](https://developer.apple.com/forums/thread/68603)
- On iOS, short clicks failed after ~3 s of silence as the output hardware sleeps; workaround: keep the session alive / near-silent output — [Apple forums 22126](https://developer.apple.com/forums/thread/22126)
- `AudioServicesPlaySystemSound` plays "a short sound (30 seconds or less in duration)" asynchronously, with no volume/pitch/voice control — [Apple: AudioServicesPlaySystemSound](https://developer.apple.com/documentation/audiotoolbox/audioservicesplaysystemsound(_:))
- VoiceInk (open-source macOS dictation app) plays its start/stop cues with `AVAudioPlayer` (fine for occasional cues, not per keystroke) — [VoiceInk SoundPlaybackEngine.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/Audio/SoundPlaybackEngine.swift)
- cpal's macOS host uses a CoreAudio `DefaultOutput` AudioUnit (follows the default device) and reads `kAudioDevicePropertyBufferFrameSize`/`BufferFrameSizeRange`; it tracks latency frames for callback timestamps — [cpal src/host/coreaudio/macos/device.rs](https://github.com/RustAudio/cpal/blob/master/src/host/coreaudio/macos/device.rs); cpal 0.18.2 — [docs.rs cpal](https://docs.rs/crate/cpal/latest)

### Inferences
- Latency budget for the click (arithmetic, not measured): trigger from the key handler into a lock-free queue (≈0) + one I/O buffer (128 frames @48 kHz = 2.7 ms; 512 = 10.7 ms) + device safety offset and output latency (device-dependent; the 720-sample report ≈ 15 ms at 48 kHz would dominate) ⇒ ~5–20 ms on built-in speakers/wired output, comparable to or below the visual path (one 120 Hz frame = 8.3 ms plus compositor). Pressing the click on key-down (not after layout/paint) keeps audio ahead of the visual change.
- Mixer design that works identically in Swift and Rust: N preloaded mono buffers per key class (letters, space, return, backspace; separate down/up sets for mechanical switches; for a typewriter mostly down-strokes plus a carriage-return/bell on Return), round-robin with "no immediate repeat", ±1–2 dB random gain and a small random playback-rate change done by the mixer's own resampling (linear interpolation is enough for clicks) instead of a TimePitch unit; 16–32 polyphonic voices with voice stealing for fast typists; stream kept running while the window is visible to avoid hardware wake-up latency.
- For a Rust/GPUI build: cpal directly (own callback mixer, `BufferSize::Fixed(128)` clamped to the device range) is simpler and more predictable than kira for this one job; kira is fine if scheduling/tweens are wanted later. AVAudioEngine is reachable from Rust via objc2 but buys nothing over cpal here.
- Licensing: ship only CC0 or self-recorded samples, or packs with explicit redistribution licences; treat Mechvibes community packs as unlicensed for redistribution unless the pack author states otherwise. Recording one's own typewriter/switches (close mic, 48 kHz, many takes per key) is the cleanest route.
- Detect Bluetooth output (CoreAudio device transport type) and warn or offer to mute clicks, since 120–300 ms is perceptibly late.

### Gaps
- No independent measurement of Klack's or any keyboard-sound app's key-to-sound latency was found.
- No measured AVAudioEngine-vs-cpal output latency on macOS was found; only buffer-size facts and anecdotes. A loopback measurement (contact mic on the key + line-in) on the target Mac is needed.
- A forum report that `AVAudioUnitTimePitch.latency` was 0.09 s (iOS) surfaced in search, but the exact thread could not be pinned down; treat as unverified (the advice to avoid time-pitch units in the click path does not depend on it).
- Whether `kAudioDevicePropertyBufferFrameSize` set by one app affects other apps on the same device on current macOS was not verified.
- Licences of Klack's own sounds (proprietary, presumably) and of specific "Cherry MX" recordings on Freesound were not checked individually.

## Text injection into the frontmost app: CGEventPost unicode, pasteboard + ⌘V, Accessibility setValue, an input method; permissions, secure input, sandbox

### Takeaway
Shipping tools converge on two paths: pasteboard + synthesized ⌘V as the default (fast, any length, works in Electron/Chromium/terminals that accept paste) and per-chunk `CGEventKeyboardSetUnicodeString` "typing" as the fallback (no clipboard side effects, 20-UTF-16-unit chunks, paced ~10 ms). Both need the PostEvent privilege (shown to users as "Accessibility"), which DTS says is sandbox-compatible but App Review has rejected for a clipboard tool under guideline 2.4.5 (2026) — so distribute outside the Mac App Store. AX `kAXSelectedTextAttribute` writes are unreliable outside native Cocoa fields, and an IMKit input method is the cleanest insertion channel but requires the user to install and switch input sources. Copy-to-clipboard should always be offered as the zero-permission baseline.

### Cited Findings

**CGEventPost with a Unicode payload ("direct typing")**
- Apple: by default the system translates the virtual key code to a string; `keyboardSetUnicodeString` overrides it, but "application frameworks may ignore the Unicode string in a keyboard event and do their own translation based on the virtual keycode" — [Apple: keyboardSetUnicodeString](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring(stringlength:unicodestring:))
- The string is truncated after 20 characters per event (undocumented); espanso's macOS injector chunks at 20 UTF-16 units when using the default delay, otherwise 1 character per event, and posts to `kCGHIDEventTap`, marking its own events with a sentinel location `(-27469, 0)` and releasing a held Shift first (issue #279) — [espanso native.mm](https://github.com/espanso/espanso/blob/dev/espanso-inject/src/mac/native.mm); [Qt forum report of 20-char limit](https://forum.qt.io/post/46576); [typechar crate (20-unit chunks, never split surrogate pairs)](https://docs.rs/crate/typechar/1.1.0)
- VoiceInk "Direct Typing": chunk size 20 ("conservative limit for compatibility with receivers that truncate longer Unicode event payloads"), 10 ms between chunks, events from `CGEventSource(stateID: .privateState)` on virtual key 0x31 (Space) carrying the Unicode payload, posted to `.cghidEventTap`; newline sent as a Shift-modified 0x0D payload to get a line break rather than a paragraph in rich editors; comment: posting via the HID tap lets macOS "route input to the current keyboard recipient, including nonactivating panels whose app is not reported as frontmost"; requires `AXIsProcessTrusted()` — [VoiceInk DirectTextTyper.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/DirectTextTyper.swift)
- Since macOS 10.14, posting events requires the user's approval (posts silently fail without it) — [Apple forums 103992](https://developer.apple.com/forums/thread/103992); check/request APIs `CGPreflightPostEventAccess`/`CGRequestPostEventAccess` exist since macOS 10.15 — [Apple: CGRequestPostEventAccess](https://developer.apple.com/documentation/coregraphics/cgrequestposteventaccess())

**Pasteboard + synthesized ⌘V**
- VoiceInk default method: write text to `NSPasteboard.general` with extra types `org.nspasteboard.source` (bundle id), optionally `org.nspasteboard.TransientType` and `org.nspasteboard.AutoGeneratedType`, plus a private session-marker type; wait 200 ms (`prePasteDelay`), post ⌘ down, V down, V up, ⌘ up (keycodes 0x37/0x09, `.maskCommand`, `.privateState` source, `.cghidEventTap`) 10 ms apart; restore the old clipboard after ≥ 250 ms (user-set, capped 5 s) only if the pasteboard still carries its session marker; alternative "AppleScript" method sends `keystroke "v" using command down` via System Events — [VoiceInk CursorPaster.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/CursorPaster.swift); [ClipboardManager.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/ClipboardManager.swift); [PasteMethod.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/PasteMethod.swift)
- espanso: `backend` = `inject` (simulated keypresses) / `clipboard` / `auto`; `clipboard_threshold` 100 chars (above it, `auto` uses the clipboard); `pre_paste_delay` 300 ms; `paste_shortcut_event_delay` 10 ms; `restore_clipboard_delay` 300 ms; `preserve_clipboard` true; `inject_delay`/`key_delay` 0–1 ms by platform — [espanso options](https://espanso.org/docs/configuration/options/); older docs/commits state `Inject` is the macOS default and `Auto` is Linux-only — [espanso mirror](https://git.nunosempere.com/open.source/espanso/commit/a480ad1a0326e8e8c2156891e5a835a3ea8a896f)
- Wispr Flow (desktop) requires Accessibility; when auto-paste fails it offers "Paste last transcript" (⌃⌘V on Mac); apps that block paste include Citrix Workspace, virtual desktops, some corporate (EMM) apps and password managers — [Wispr Flow docs](https://docs.wisprflow.ai/articles/7971211038-fix-text-not-pasting-after-dictation)
- Pasteboard privacy (macOS 15.4+ API): `NSPasteboard.AccessBehavior` — for the general pasteboard the default is "ask upon programmatic access"; "access that is both user originated and paste related will always be allowed"; `detect` methods inspect types without reading or alerting — [Apple: NSPasteboard.AccessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum); [Michael Tsai: Pasteboard Privacy Preview in macOS 15.4](https://mjtsai.com/blog/2025/05/12/pasteboard-privacy-preview-in-macos-15-4/); [Lapcat: Making my app worse because of macOS privacy protections](https://lapcatsoftware.com/articles/2025/5/3.html)
- Enforcement status is unclear: a mid-2026 article says the alert was announced but "not enforced by default"; a 2025 post says it seemed absent in macOS 26 unless enabled via a developer default (`EnablePasteboardPrivacyDeveloperPreview`) — [dev.to (2026)](https://dev.to/jrw0ng/macos-tahoe-has-built-in-clipboard-history-heres-what-its-still-missing-for-developers-2026-4eko); [Appletreats](https://appletreats.substack.com/p/macos-16-will-warn-when-apps-access)
- macOS 26.4 adds a separate Terminal paste protection: Terminal checks which app put content on the pasteboard (list of 74 apps) and may warn/block ClickFix-style pastes; suppressed if Terminal was opened in the last 30 days or developer tools are installed — [Michael Tsai: macOS 26.4 Paste Protection](https://mjtsai.com/blog/2026/04/03/macos-26-4-paste-protection/)
- Synthetic ⌘V events can be distinguished from real ones (real ones come from pid 0, the HID system) — [claudeissues.com #26544](https://claudeissues.com/issue/26544-claude-code-node-process-posts-phantom-cmd-v-cgevent-system-wide-on-macos)

**Accessibility API (AXUIElement)**
- Electron apps are a weak spot for AX text manipulation; Electron needs `AXManualAccessibility` set to expose its tree (PR #38102 fixed it reporting failure); Chromium's native Views text fields replace the selection when the selected-text attribute is set (Omnibox/dialogs, not necessarily web content); WebKit has had bugs with setValue/contenteditable selected-text attributes — [electron#38102](https://github.com/electron/electron/pull/38102); [Chromium review 2341633006](https://codereview.chromium.org/2341633006); [WebKit bug 48080](https://bugs.webkit.org/show_bug.cgi?id=48080); [Obsidian forum](https://forum.obsidian.md/t/macos-text-replacement-doesnt-work/1269/2)
- Flutter text fields are not detected by external dictation tools on macOS (open, 2026) — [flutter#191503](https://github.com/flutter/flutter/issues/191503)
- `kAXErrorCannotComplete` is a common symptom when the target's AX tree is not exposed — [Apple forums 740000](https://developer.apple.com/forums/thread/740000)
- VoiceInk uses AX only to read context/selection (`AccessibilityTextReader`, `SelectedTextService`), not to insert — [VoiceInk repo tree](https://github.com/Beingpax/VoiceInk/tree/main/VoiceInk/Infrastructure/SystemIntegration)

**Input method (InputMethodKit)**
- An IMKit input method commits text by calling `insertText:replacementRange:` on the client (`IMKTextInput`), without the pasteboard — [Apple NumberInput IMKit sample](https://developer.apple.com/library/archive/samplecode/NumberInput_IMKit_Sample/Listings/trunk_NumberInput_4_NumberInputController_m.html); [objc2-input-method-kit](https://docs.rs/objc2-input-method-kit/)
- Developers report IMKit input methods that register and can be selected but block keyboard input on macOS 15.2 — [Apple forums 789199](https://developer.apple.com/forums/thread/789199)

**Secure input**
- `EnableSecureEventInput` (used by password fields) prevents keyboard events being intercepted by other processes (event taps); state is queryable with `IsSecureEventInputEnabled()`; apps can leave it stuck on (OmniWeb example) — [Apple TN2150](https://developer.apple.com/library/mac/technotes/tn2150/_index.html); [Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/determine-if-the-system-is-in-secure-input-mode/858); [Omni forum](https://discourse.omnigroup.com/t/bug-omniweb-enables-secure-input-when-it-shouldn-t/50436)

**TCC privileges, sandbox, App Store**
- DTS (Quinn, Mar 2026): three privileges — `ListenEvent` (Input Monitoring), `PostEvent` (posting UI events, e.g. `CGEvent.post`), `Accessibility` (AX APIs); "Both PostEvent and Accessibility map to Accessibility" in System Settings; "The APIs gated by the Accessibility privileged are not compatible with the App Sandbox"; PostEvent and ListenEvent "are compatible with the App Sandbox" — [Apple forums 820594](https://developer.apple.com/forums/thread/820594)
- Same thread: a sandboxed clipboard manager that writes to the pasteboard and posts ⌘V was rejected twice under Guideline 2.4.5 ("Accessibility features should not be used for non-accessibility purposes", paraphrased); others reported the same in Sep 2026 — [Apple forums 820594](https://developer.apple.com/forums/thread/820594)
- Older guidance: the App Sandbox design guide said posting events with `CGEventPost` circumvents the sandbox and is not allowed; in 2015 Quinn said CGEventPost access would let an app defeat the sandbox — [Apple forums 28605](https://developer.apple.com/forums/thread/28605); in Jun 2022 he suggested `CGRequestPostEventAccess`/`CGPreflightPostEventAccess` and said the explicit user approval introduced in 10.15 "means that it's now allowed in the App Sandbox", hedged: his check was for Input Monitoring, "YMMV", and only App Review can say what the App Store accepts — [Apple forums 708652](https://developer.apple.com/forums/thread/708652)

### Inferences
- Recommended injection pipeline: (1) on commit, hide/close the panel (with a non-activating panel the target app never lost activation, see next sections); (2) if `IsSecureEventInputEnabled()` is true, do not inject — copy and tell the user; (3) default to pasteboard + ⌘V for text longer than ~20–100 characters, writing `org.nspasteboard.TransientType`/`AutoGeneratedType`/`source` so clipboard managers skip it, then restore the previous contents after ~250–500 ms only if `changeCount` still matches; (4) offer "type" mode (20-unit chunks, ~10 ms pacing, never splitting surrogate pairs) for apps that block paste, and for short strings; (5) always keep "copy only" as a no-permission mode.
- Clipboard restore needs a programmatic read of the user's previous pasteboard before writing; under the 15.4+ privacy model that read is not "user originated and paste related", so if Apple enforces the alert by default the save/restore step would trigger it. Writing alone and using `detect` APIs do not. Design the restore to be optional and degrade to "your clipboard now holds the text".
- Type mode limitations: ~10 ms per 20 units ⇒ ~2,000 characters/s at best; apps that ignore the Unicode payload will instead see the Space key (VoiceInk) or the keycode in the event — test in Terminal, VS Code/Electron, Chrome, Java/JetBrains, Word, Google Docs.
- An IMKit input method is the only channel that writes through each app's own `NSTextInputClient` (the same path IMEs use, which Electron/Chromium/Java implement for CJK), but the user must add and select the input source, and it is a separate bundle in `~/Library/Input Methods`; it is a poor default for a hotkey-summoned writer, but a viable "pro" option.
- App Store: given the 2026 2.4.5 rejections, plan for Developer ID distribution (notarized) outside the Mac App Store; injection is the reason.

### Gaps
- Whether a CGEventPost'ed Unicode event reaches a password/secure field while Secure Event Input is on was not confirmed by any source (TN2150 is about interception, not posting).
- Whether Universal Clipboard (Handoff) honours `org.nspasteboard.TransientType` and skips syncing was not confirmed; the nspasteboard.org markers are a community convention, not an Apple API.
- Superwhisper's exact insertion mechanism was not found in its docs; Wispr Flow's desktop docs do not say whether paste or keystrokes are the default.
- A per-app compatibility matrix (Electron, Chromium web content, Terminal/iTerm2, Java/JetBrains, Citrix, Office) for each method was not found; must be built by testing.
- Rate limits on CGEventPost beyond the 20-unit truncation are undocumented; the 10 ms pacing used by VoiceInk/espanso is empirical.

## Dimming the rest of the screen

### Takeaway
Use one borderless, mouse-transparent, black, partly transparent `NSWindow` per `NSScreen`, joined to all Spaces and allowed over full-screen apps, ordered directly below the writing panel; this needs no permission because only the app's own panel is left undimmed. HazeOver's "dim everything but the frontmost window of another app" needs Accessibility to track other apps' windows, which this app does not need. Focus integration is limited to reacting to Focus changes (`SetFocusFilterIntent`, macOS 13+).

### Cited Findings
- HazeOver places "a translucent dark layer behind the current window", shades the window you leave, offers instant or animated transitions (a reviewer preferred ~0.40 s), per-window or per-app highlight, multi-display options, and recommends granting Accessibility so it reacts instantly to window switches and detects the focused window reliably — [HazeOver help](https://HazeOver.com/help.html); [Macworld review](https://www.macworld.com/article/227329/hazeover-1-6-review-dim-those-background-windows-so-you-can-focus-on-the-task-at-hand.html)
- `NSWindow.ignoresMouseEvents`: "whether the window is transparent to mouse events" — [Apple: ignoresMouseEvents](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents)
- `NSWindow.CollectionBehavior.fullScreenAuxiliary` (macOS 10.7+): "The window displays on the same space as the full screen window"; GPUI's PopUp panels already use `CanJoinAllSpaces | FullScreenAuxiliary` at `NSPopUpWindowLevel` (101) — [Apple: fullScreenAuxiliary](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/fullscreenauxiliary); [gpui-pre-macos 0.3.8 src/window.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/window.rs)
- `SetFocusFilterIntent` (App Intents; macOS 13.0+) lets an app adapt its behaviour when a Focus changes (WWDC22 "Meet Focus filters") — [Apple: SetFocusFilterIntent](https://developer.apple.com/documentation/appintents/setfocusfilterintent)
- Reduce Motion is exposed as `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` (macOS 10.12+) — [Apple: accessibilityDisplayShouldReduceMotion](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion)

### Inferences
- Overlay recipe (AppKit/objc2): for each `NSScreen.screens`, an `NSWindow`/`NSPanel` with `styleMask = .borderless`, `backgroundColor = .black`, `alphaValue` 0.4–0.7 (or a `CALayer` with opacity for animated fades), `isOpaque = false`, `ignoresMouseEvents = true`, `hasShadow = false`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]`, level one below the writing panel (e.g. panel at `.popUpMenu`/101, overlay at `.floating` or `popUp − 1`), never key or main (`canBecomeKey = false`). Fade in/out ~150–250 ms unless Reduce Motion, then instant. Rebuild on `NSApplication.didChangeScreenParametersNotification`.
- Because the overlay ignores mouse events, a click "through" it activates the app beneath; decide whether a click outside the panel should dismiss the panel (Spotlight-like) — listen with a local/global mouse monitor or panel `resignKey`.
- Menu bar and Dock: a window at these levels covers the menu bar; leave a gap (`NSScreen.visibleFrame`) if the menu bar should stay visible.
- Do Not Disturb: no public API to turn a Focus on was found; the app can only respond to Focus via a Focus filter, or suggest the user bind a Focus to the app.
- GPUI can create these overlay windows itself (transparent background, PopUp kind), but setting `ignoresMouseEvents`/exact levels likely needs a few objc2 calls on the native `NSWindow` handle.

### Gaps
- Stage Manager interaction (whether all-Spaces/auxiliary overlays are grouped into a stage or float above the strip) was not researched; needs testing on macOS 15/26.
- Whether screen recording/screenshots should exclude the overlay (`sharingType = .none`) is a product choice; not researched.

## Window summoning: global hotkey, non-activating panel, keeping the previous app frontmost, restoring focus

### Takeaway
Register the hotkey with Carbon `RegisterEventHotKey` (no permission, sandbox-safe; avoid Option-only/Shift-Option-only combos, which Sequoia blocks for sandboxed apps), show a non-activating `NSPanel` that becomes key so it receives typing while the previous app stays the active app, then close the panel and inject — no reactivation dance is needed. If the app ever activates itself, macOS 14's cooperative activation (`yieldActivation(to:)` + `activate()`) is required to hand focus back and is not guaranteed.

### Cited Findings
- Carbon global hotkeys: sindresorhus/KeyboardShortcuts uses Carbon for registering global shortcuts, causes no permission dialogs, and is "fully sandboxed and Mac App Store compatible" (macOS 10.15+) — [KeyboardShortcuts](https://github.com/sindresorhus/KeyboardShortcuts)
- Since macOS Sequoia, global hotkeys whose only modifiers are Option or Shift+Option no longer work for sandboxed apps (developer report; "intentional"; non-sandboxed apps appear unaffected); Apple forum thread "Using RegisterEventHotkey with option and shift modifiers doesn't working anymore" (Sep 2024) — [Shottr KB](https://shottr.cc/kb/sequoia)
- `NSEvent.addGlobalMonitorForEvents`: key events only if trusted for Accessibility; observe-only — [Apple: addGlobalMonitorForEvents](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:)); `CGEventTap` listen-only needs Input Monitoring, a default (filtering) tap triggers the Accessibility prompt — [Apple forums 707680](https://developer.apple.com/forums/thread/707680); `CGRequestListenEventAccess` sometimes does not add the app to the Input Monitoring list on macOS 15 — [Apple forums 828052](https://developer.apple.com/forums/thread/828052)
- `.nonactivatingPanel`: "The window is a panel or a subclass of NSPanel that does not activate the owning app"; with `becomesKeyOnlyIfNeeded`, a non-activating panel becomes key only if the hit view returns true from `needsPanelToBecomeKey` — [Apple: nonactivatingPanel](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel); [Apple: becomesKeyOnlyIfNeeded](https://developer.apple.com/documentation/appkit/nspanel/becomeskeyonlyifneeded)
- `NSWorkspace.frontmostApplication`: "the app that receives key events" (KVO-compliant) — [Apple: frontmostApplication](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication); VoiceInk's code notes non-activating panels "whose app is not reported as frontmost" still receive keyboard input — [VoiceInk DirectTextTyper.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/DirectTextTyper.swift)
- Electron: a `type: "panel"` window was expected to keep the previous window focused but broke on Sonoma; a commenter notes `NSWindow` (not `NSPanel`) does not support the non-activating style mask — [electron#35815](https://github.com/electron/electron/issues/35815)
- Old Cocoa-dev reports: programmatically resigning key on a non-activating panel is fragile; `[NSApp deactivate]` resigns key without deactivating — [cocoa-dev 2002](https://lists.apple.com/archives/cocoa-dev/2002/Sep/msg01432.html)
- macOS 14: `activateIgnoringOtherApps` deprecated; `NSApplication.activate()` (14.0+) "Activates the receiver app, if appropriate"; cooperative activation: the active app calls `yieldActivation(to:)` / `yieldActivation(toApplicationWithBundleIdentifier:)`, then the target calls `activate()`; `NSRunningApplication.activate(from:options:)` (14.0+) is not guaranteed — [Apple: activate()](https://developer.apple.com/documentation/appkit/nsapplication/activate()); [Apple: Passing control from one app to another with cooperative activation](https://developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation); [Apple: activate(from:options:)](https://developer.apple.com/documentation/appkit/nsrunningapplication/activate(from:options:)); [MacVim issue 1456 (mirror)](https://identichosting.duckdns.org/macvim-dev/macvim/issues/1456)
- A yield silently fails when the yielding app is not frontmost; Wine notes yields to bundle IDs can be cancelled if the user clicks/types/moves a window in the yielding app — [Apple forums 793253](https://developer.apple.com/forums/thread/793253); [Wine GitLab list](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/K4XSASJC5FYH262CAN453KE4ZHNRCKDX/)
- GPUI's `WindowKind::PopUp` produces exactly a non-activating `NSPanel` (style mask `NSWindowStyleMaskNonactivatingPanel`, level 101, all Spaces + full-screen auxiliary, utility-window animation) — [gpui-pre-macos 0.3.8 src/window.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/window.rs)

### Inferences
- Flow: hotkey (Carbon) → record `NSWorkspace.frontmostApplication` (for UI hints and per-app injection settings) → show non-activating panel, `makeKeyAndOrderFront` → user types (all text input goes to the panel's `NSTextInputClient`, IME works) → on commit `orderOut` the panel → inject into the still-active app. No activation, no yield, no race with macOS 14 activation rules.
- App should be an agent app (`LSUIElement = YES` / accessory activation policy, which GPUI supports) with an `NSStatusItem` (objc2 in a GPUI build) for the menu-bar icon.
- Pick a default hotkey with ⌘ or ⌃ to avoid the Sequoia Option-only restriction; allow rebinding.
- Use `CGEventTap`/global monitors only if the app must observe typing elsewhere (it does not for this design), avoiding the Input Monitoring prompt entirely.

### Gaps
- No Raycast/Alfred engineering post confirming their panel/focus approach was found; the conclusion rests on Apple docs, VoiceInk's code comment, and GPUI's implementation.
- Behaviour of a key non-activating panel over a full-screen app on macOS 26 and with Stage Manager was not verified by a source.

## Smooth horizontal text scroll at 120 Hz with a fixed caret: crisp text at fractional offsets, dimming/blurring the rest, Reduce Motion

### Takeaway
Shape the line once per edit, then each display-link frame translate it by an animated offset so the caret stays fixed; keep ProMotion at 120 Hz by presenting every frame during the motion (Zed's trick). For crispness, either render glyphs at subpixel x-positions from a glyph atlas (GPUI already keeps 4 horizontal subpixel variants per glyph with Core Text subpixel positioning; macOS has used grayscale AA since Mojave, so no color fringing) or move a pre-rendered line texture/layer at fractional offsets during motion and snap to whole pixels at rest — the standard WPF/GTK compromise. Honour Reduce Motion by jumping instead of sliding.

### Cited Findings
- GPUI glyph rasterization: `SUBPIXEL_VARIANTS_X = 4`, Core Text subpixel positioning on, subpixel quantization off, grayscale AA, an extra pixel of padding for non-zero variants — [gpui-pre 0.3.8 src/text_system.rs](https://docs.rs/crate/gpui-pre/0.3.8/source/src/text_system.rs); [gpui-pre-macos 0.3.8 src/text_system.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/text_system.rs)
- macOS Mojave disabled subpixel (LCD) antialiasing by default (re-enable via `CGFontRenderingFontSmoothingDisabled`, not recommended) — [Stanislas blog](https://stanislas.blog/2018/09/how-to-fix-font-rendering-macos-10-14-mojave/)
- Pixel snapping causes content to "jump from one pixel to the next" during slow animations, which "causes jitter" (GTK); GTK text views scrolled by 0.5-logical-pixel steps jitter during kinetic deceleration — [GNOME/GTK blog](https://blogs.gnome.org/chergert/?p=10314); [GNOME discourse: snapping](https://discourse.gnome.org/t/snapping/35214)
- WPF detects text animation/scrolling, turns off pixel snapping during motion and back on afterwards (text appears to sharpen ~1 s after the animation) — [Microsoft archive blog](https://learn.microsoft.com/fr-fr/archive/blogs/seema/after-animating-text-the-text-seems-to-pause-for-1-second-and-then-render-more-sharply-than-before-why-is-that)
- Per-glyph rounding makes text "jiggle" during animation; subpixel glyph positioning keeps kerning stable as text moves — [OpenJFX mailing list](https://mail.openjdk.org/pipermail/openjfx-dev/2013-May/008028.html)
- ProMotion downclocks when frames stop; Zed presents on every display-link callback for 1 s after input to hold 120 fps — [Zed blog](https://zed.dev/blog/120fps); `CADisplayLink.preferredFrameRateRange` (macOS 14+) states the desired rate — [Apple](https://developer.apple.com/documentation/quartzcore/cadisplaylink/preferredframeraterange)
- Reduce Motion: `NSWorkspace.accessibilityDisplayShouldReduceMotion` (10.12+) — [Apple](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion)
- GPUI window background can be `Blurred` (system blur of what is behind the window, not of the window's own content) — [gpui-pre 0.3.8 src/platform.rs](https://docs.rs/crate/gpui-pre/0.3.8/source/src/platform.rs)

### Inferences
- Motion model: on each keystroke the target offset jumps by the advance of the typed glyph(s); animate the visible offset toward it with a critically damped spring or a short ease-out (~50–80 ms ≈ 6–10 frames at 120 Hz) so fast typing (10+ chars/s) never lags more than a fraction of a character; Reduce Motion → offset = target immediately.
- GPUI route: one shaped line (`ShapedLine`) per edit, painted at `origin.x = caret_x − offset`; at 4 subpixel variants the line moves in 0.25 px steps at 2× scale (0.125 pt), which is visually continuous; variant switching causes faint per-glyph shimmer during motion that is generally acceptable and vanishes at rest. Dimming the rest of the text is a per-run colour/alpha (cheap); a real Gaussian blur of the text away from the caret would need a custom shader or an offscreen pass, which GPUI does not expose as a public element effect (not verified).
- AppKit route: draw the line with Core Text into a `CALayer` once per edit (at backing scale), then animate the layer's `position`/`transform` with Core Animation; CA interpolates in the render server off the main thread at display rate, and fractional positions are resampled (slight softness during motion, crisp when the final position is pixel-aligned). Blur/dim of the surrounding text: a `CAGradientLayer` mask for dimming; `layer.filters` with `CIGaussianBlur` (macOS supports Core Image filters on layers) for blur — not verified for performance.
- Avoid relayout per frame: shaping and layout happen once per edit; per-frame work is a translation, which keeps frame time far under the 8.3 ms budget in any stack.

### Gaps
- No source measured perceived crispness of 4-variant subpixel positioning vs. texture translation on Retina displays; needs an A/B prototype.
- Performance of Core Image blur on CALayers at 120 Hz on Apple Silicon was not researched.
- Whether GPUI exposes a custom shader/paint hook suitable for a blur effect in the current snapshot was not checked.

## Cross-platform later: which stack ports with least rewrite; GPUI on Linux/Windows in 2026; Swift on Linux/Windows

### Takeaway
GPUI ports best for this implementer: Zed ships stable on macOS, Linux (X11/Wayland, now via wgpu) and Windows (DirectX 11 + DirectWrite, stable since 15 Oct 2025), and GPUI's platform crate also targets wasm. But the OS-integration half of this app (global hotkey, non-activating panel, injection, overlays, permissions) is per-OS code in every stack; only the UI/text/sound core is shared. Swift on Windows/Linux for UI is not realistic for a small app: The Browser Company needed custom WinRT bindings and WinUI 3 to ship Arc on Windows.

### Cited Findings
- Zed for Windows: stable build available (blog dated 15 Oct 2025), "fully supported platform", DirectX 11 rendering with DirectWrite text; Zed asked for feedback on IME, keyboard layouts, multi-monitor and high-refresh displays — [Zed blog: Windows When? ### Inferences
- Rewrite estimate per stack for adding Windows/Linux: GPUI — UI, text, sound (cpal is cross-platform) carry over; rewrite the platform shim (Windows: `RegisterHotKey`, `SendInput` with `KEYEVENTF_UNICODE`, layered topmost overlay windows, `WS_EX_NOACTIVATE` panel; Linux X11: XTest/xdotool-style injection, Wayland: compositor-dependent, often impossible without uinput/portals). Swift+AppKit — rewrite the whole UI and shim (WinUI/GTK), keep only model code. Tauri/Flutter — UI carries over, same shim rewrite as GPUI, plus per-engine IME quirks.
- Wayland is the weakest target for "type into the focused app" and global hotkeys in any stack; espanso's evdev route needs elevated input access. Ship macOS first, then Windows; treat Linux injection as best-effort/copy-only.

## Recommended stack and the specific macOS API for each need

### Takeaway
For this implementer: Rust + GPUI (pinned snapshot) for the window, text input, shaping and 120 Hz painting, plus a thin objc2 macOS layer (status item, hotkey, overlay windows, CGEvent/pasteboard injection, TCC checks) and a cpal output stream with an own sample mixer. It reuses existing GPUI skill, gets correct IME/dead keys via Zed's maintained `NSTextInputClient`, already provides a non-activating panel, and keeps the Windows/Linux UI path open. Swift + AppKit is the strongest alternative if macOS-only is acceptable and binary size/accessibility weigh more than reuse; its cost is learning AppKit/Core Animation and a full UI rewrite later. Avoid Electron, and avoid egui/iced/raw winit because of open macOS dead-key bugs.

### Cited Findings
- (All supporting citations are in the sections above; the API list below repeats the primary references.)
- Text input: `NSTextInputClient` (`insertText:replacementRange:`, `setMarkedText:selectedRange:replacementRange:`, `unmarkText`, `firstRectForCharacterRange:actualRange:`), reached from `keyDown:` via `interpretKeyEvents:` — [Apple](https://developer.apple.com/documentation/appkit/nstextinputclient); GPUI implements it — [gpui-pre-macos window.rs](https://docs.rs/crate/gpui-pre-macos/0.3.8/source/src/window.rs)

- Reduce Motion: `NSWorkspace.accessibilityDisplayShouldReduceMotion` (10.12+) — [Apple](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion)

- Distribution: Mac App Store requires the sandbox; PostEvent is sandbox-compatible per DTS but App Review rejected a ⌘V-posting clipboard tool under 2.4.5 in 2026 — [Apple forums 820594](https://developer.apple.com/forums/thread/820594)

### Inferences
- Need → API → minimum macOS (for a macOS 14+ deployment target, which unlocks `NSView.displayLink` and cooperative activation):
  1. Scrolling line, fixed caret, 120 Hz: GPUI frame loop (CVDisplayLink today) or `NSView.displayLink` + `preferredFrameRateRange` (14+); hold 120 Hz by presenting every frame while animating; Reduce Motion via `accessibilityDisplayShouldReduceMotion` (10.12+).
  2. Text input: `NSTextInputClient` via GPUI's `EntityInputHandler` (or a custom `NSView` in Swift); test ⌥E E, ⌥` A, ⌥U O, ⌥N N, Pinyin, Kotoeri, emoji picker (⌃⌘Space), dictation.
  3. Click sound: cpal stream (CoreAudio DefaultOutput AU), preloaded PCM, own mixer, 64–128-frame buffer; trigger on key-down in the window's own handler; no permission needed.
  4. Inject: pasteboard + ⌘V (default) / Unicode CGEvent chunks (fallback) / copy-only; PostEvent privilege (10.15+ request API), check `IsSecureEventInputEnabled()`; restore clipboard optionally (15.4+ privacy model caveat).
  5. Dim: per-screen borderless overlay windows below the panel; no permission.
  6. Summon: Carbon `RegisterEventHotKey` with ⌘/⌃ modifiers; non-activating `NSPanel` (GPUI `WindowKind::PopUp`); accessory activation policy + `NSStatusItem` via objc2; distribute via Developer ID + notarization.
- Risks of the GPUI choice: pre-1.0 API churn (pin `gpui-pre`/`gpui` version and bump deliberately), larger binary than Swift (tens of MB), occasional IME regressions (test matrix above), no status-item API (≈50 lines of objc2).
- What would flip the recommendation to Swift + AppKit: a hard size target of a few MB, a requirement for App Store distribution of a copy-only edition (Swift integrates best with sandbox/StoreKit), or VoiceOver-grade accessibility from day one.

### Gaps
- A side-by-side prototype (GPUI vs AppKit) measuring key-to-photon latency (high-speed camera or Typometer), cold launch, and binary size is the missing evidence for the final choice.
- Exact App Review stance for a writing tool (not a clipboard manager) that posts ⌘V is unknown; only DTS's technical view and one rejection thread exist.
